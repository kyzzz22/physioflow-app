# PhysioFlow 系统业务分析与重构开发计划书

版本：v1.0（重构立项稿）

日期：2026-08-22

适用分支：`demo` 后续重构

## 1. 项目定位

PhysioFlow 的目标不是提供一组固定实验模板，而是提供一个面向行为学、心理学和生理信号实验的可视化实验系统 Composer。用户应能在同一个工作空间中：

- 编排实验逻辑：顺序、条件、循环、随机化、重复、暂停和恢复；
- 设计参与者界面：文字、图片、视频、问卷、按钮、量表和自定义组件；
- 定义数据契约：每个组件产生什么事件、变量和导出字段；
- 预览、验证、冻结、运行并导出一次实验的完整记录。

产品核心价值是降低实验系统设计和使用的门槛，同时保留研究人员需要的高度可控性、可复现性和数据完整性。

## 2. 当前系统的业务问题

现有系统已经具备流程画布、问卷设计、运行时、协议冻结、会话日志和 ZIP 导出等能力，但产品抽象仍偏向“带可视化编辑器的协议表单”。主要问题如下：

1. `Block / Trial / Step / Flow Node` 多套结构同时描述实验顺序，导致用户需要维护重复信息。
2. 运行时界面由固定 React 组件决定，主题和少量样式可配置，但页面无法真正组合。
3. `Custom HTML` 是自由度逃生舱，不是可管理、可验证、可记录的自定义组件体系。
4. 条件节点依靠字符串变量，缺少变量类型、作用域、来源、输入输出和数据流可视化。
5. Inspector 承担过多配置，简单实验与高级实验没有渐进式复杂度分层。
6. 事件导出已有基础，但还没有形成从组件定义到运行日志再到分析文件的统一数据契约。
7. 组件、运行时、验证器、导出器和编辑器之间存在大量按类型分支，新增能力的维护成本会线性增长。

因此，本次工作应优先重建领域模型和用户主路径，再迁移现有功能；不应继续在现有 Step 类型上叠加更多开关。

### 2.1 目标与现状差距矩阵

| 业务目标 | 当前状态 | 核心差距 | 重构方向 |
| --- | --- | --- | --- |
| 像 Infrastructure Composer 一样快速编排 | 已有画布，但 Step 与 Flow 并存 | 画布不是唯一事实来源，概念和操作路径重复 | 统一为 Protocol Graph，所有执行单元均为节点实例 |
| 高度自定义实验逻辑 | 支持条件、循环、重复和随机化 | 变量靠字符串引用，端口与作用域不清晰 | 类型化变量、控制端口、数据端口和可视化表达式 |
| 自定义参与者界面的全部元素 | 预制运行组件加少量 appearance 配置 | 不能组合页面结构，Custom HTML 无法纳入标准运行与数据体系 | 声明式 UI 组件树、属性绑定和动作系统 |
| 导出实验全过程数据 | 已有事件、响应、窗口和完整性报告 | 缺少组件级数据契约、环境快照和统一 schema 版本 | Event Envelope、原始 JSONL、派生表和数据字典 |
| 易学易用 | 功能入口较多，Inspector 配置密集 | 简单任务过早暴露高级概念 | Quick Build / Design / Advanced 渐进式模式 |
| 可扩展 | 新类型需修改多个核心文件 | 编辑、运行、校验和导出按类型耦合 | Component Registry 与稳定的组件 SDK |

### 2.2 本次重构的业务边界

本次重构首先解决“实验定义、执行、记录”这一条核心链路，不同时扩张为实验室管理平台。项目、参与者招募、排程、团队权限、云端协作和统计分析可以在核心模型稳定后作为独立业务域接入。

首期应坚持三个边界：

- 保留本地优先和桌面优先，不把云服务作为运行前提；
- 保证正式实验的确定性和可追溯性优先于无限制脚本自由；
- 旧版本进入维护状态，只修复阻塞数据安全和迁移的问题。

## 3. 产品原则

### 3.1 画布是主要工作面

用户首先看到的是实验结构，而不是配置表单。画布展示控制流和数据流；属性面板只展示当前节点最重要的配置，高级选项按需展开。

### 3.2 一个事实来源

实验图是可执行协议的唯一事实来源。节点、端口、容器、变量和界面定义都由同一个协议模型描述，不能再让 Steps 与 Flow 双向同步。

### 3.3 组件优先

每个可执行单元都是组件，组件同时声明：显示方式、配置项、输入输出、完成条件、事件和导出字段。

### 3.4 默认简单，高级可扩展

创建“说明—刺激—回答”的简单实验应只需要几步；随机化、条件、循环、同步、分析窗口和恢复策略应在用户需要时出现。

### 3.5 可复现和可审计

正式运行必须绑定冻结版本、组件版本、随机种子、运行环境、资源校验和事件 schema。任何结果都能追溯到当时执行的配置。

### 3.6 设计即数据

用户在设计阶段就应能看到某个组件会产生哪些事件、变量和导出字段，并可以选择日志详细程度。

## 4. 目标用户与典型场景

### 4.1 实验设计者

不一定会编程，需要快速创建实验、编辑参与者界面、设置条件和导出数据。

### 4.2 实验操作员

需要清晰的运行前检查、设备检查、参与者信息录入、暂停恢复、异常处理和实时标记。

### 4.3 数据分析人员

需要稳定的 CSV/JSON schema、完整时间线、响应记录、刺激 provenance、随机化记录和质量报告。

### 4.4 高级开发者

需要定义自定义组件、组件模板、数据字段、事件和验证规则，而不是直接修改核心运行时。

典型业务闭环：

```text
创建项目 → 拖拽组件 → 配置界面与逻辑 → 预览 → 验证 → 冻结版本
→ 录入参与者并运行 → 自动记录事件 → 导出完整包 → 分析与复现
```

## 5. 目标领域模型

### 5.1 Project

项目是资源、协议、组件和运行记录的容器。

```text
Project
├── Protocol versions
├── Component definitions
├── Assets
├── Data schemas
└── Sessions
```

### 5.2 Protocol

Protocol 是一个可冻结、可执行的实验图。它不再以 `blocks/trials/steps` 作为唯一组织方式，而是由容器节点、执行节点和连接组成。

```text
Protocol
├── metadata
├── graph: nodes + edges
├── variables
├── randomization
├── participant_ui
├── data_schema
├── assets
└── version metadata
```

Block、Trial 可以作为可选的语义容器或组件模板存在，但不能再和 Flow 并列成为第二套执行模型。

### 5.3 Component

组件是编辑器、运行时、验证器和导出器共同理解的最小单元。

```json
{
  "component_type": "rating_scale",
  "component_version": "1.0.0",
  "config": {},
  "inputs": {},
  "outputs": {},
  "completion": {},
  "events": [],
  "data_fields": [],
  "appearance": {},
  "validation": []
}
```

首批内置组件建议包括：说明、图片、视频、音频、固定注视、计时器、单选/多选、量表、文本输入、反应按钮、注意力检查、操作员确认、设备检查、条件、循环、随机化和子流程。

### 5.4 UI Definition

参与者界面应作为组件树保存，而不是由 Step 类型隐式决定。

```text
Screen
└── Layout container
    ├── Text
    ├── Media
    ├── Input
    ├── Button
    └── Progress / status
```

UI 元素需要支持属性绑定，例如 `{{stimulus.label}}`、`{{response.rating}}`，并声明事件动作，例如提交答案、跳转端口、记录标记或结束组件。

### 5.5 Variable and Data Contract

变量必须包含名称、类型、作用域、来源、默认值和导出策略。

```text
participant_id: string / session
current_condition: enum / trial
rating: number / component
reaction_time_ms: number / component
attention_passed: boolean / trial
```

条件编辑器应优先从变量目录中选择，而不是让用户手写字符串。

### 5.6 Event

所有运行事件采用统一 envelope：

```json
{
  "event_id": "...",
  "session_id": "...",
  "protocol_version": "...",
  "node_id": "...",
  "component_instance_id": "...",
  "event_type": "response_submitted",
  "timestamp_iso": "...",
  "elapsed_monotonic_ms": 1234,
  "payload": {},
  "schema_version": "1.0"
}
```

## 6. 目标用户体验

### 6.1 三种编辑模式

1. **Quick Build**：只显示画布、组件库和关键属性，适合首次创建。
2. **Design**：增加界面布局、变量、分支和数据字段配置。
3. **Advanced**：显示 JSON/schema、恢复策略、同步、随机种子和自定义组件能力。

三种模式操作同一个模型，不能产生三个互不兼容的编辑结果。

### 6.2 画布布局

- 左侧：可搜索的组件库，按“展示、交互、控制、数据、容器”分组；
- 中间：实验图和数据流；
- 右侧：当前节点 Inspector；
- 底部：验证错误、变量引用和事件预览；
- 顶部：预览、运行、保存、版本和导出。

### 6.3 Inspector 分层

默认只显示：名称、内容、完成条件、关键输出。高级配置进入折叠区。每项配置旁边应显示“影响运行什么”和“产生哪些数据”。

### 6.4 预览优先

每个组件都必须可以单独预览；整个协议可以按真实运行时顺序预览。预览应展示当前变量、分支结果、事件日志和导出样例。

## 7. 功能范围

### 7.1 MVP 必须完成

- 单一图模型和 schema 版本；
- 画布拖拽、连接、复制、分组、子流程入口；
- 组件库和统一 Inspector；
- 说明、媒体、量表、按钮、文本、条件、循环、结束等核心组件；
- UI 组件树的基础布局；
- 变量目录和类型化条件；
- 统一运行时事件 envelope；
- 完整会话导出：配置、资源清单、事件、响应、环境、质量报告；
- 协议验证、冻结、版本和迁移；
- 旧协议导入和只读兼容模式。

### 7.2 第二阶段

- 自定义组件 SDK；
- 组件模板和项目级组件库；
- 子流程参数化；
- 外部问卷和外部设备连接器；
- 高级界面动画和响应式布局；
- 运行中变量检查器和调试回放。

### 7.3 暂不纳入首期

- 在线多人协作；
- 云端实验管理平台；
- 任意 JavaScript 直接注入主运行时；
- 自动统计分析和领域结论生成；
- 同时支持所有生理设备协议。

## 8. 技术重构方案

### 8.1 分层结构

```text
packages/core-model
  schema, migrations, ids, validation
packages/component-runtime
  built-in components, lifecycle, event emission
packages/editor
  canvas, palette, inspector, UI builder
packages/session-runtime
  execution, recovery, randomization, clock
packages/export
  event normalization, CSV/JSON/ZIP, data dictionary
packages/storage
  browser/Tauri adapters, assets, snapshots
```

React 只负责编辑器和界面渲染；执行状态、协议校验和导出逻辑应尽量放在纯函数模块中，便于单元测试和桌面/网页复用。

### 8.2 组件注册表

每种组件通过 registry 注册：

- `type` 与版本；
- 默认配置；
- 编辑器面板；
- 预览组件；
- 运行时生命周期；
- 输入输出 schema；
- 事件定义；
- 验证器；
- 导出映射。

新增组件不应要求在多个大型 `if/switch` 文件中同步添加逻辑。

### 8.3 兼容与迁移

采用明确的 schema migration：

1. 读取旧协议；
2. 转换为统一图模型；
3. 生成迁移报告；
4. 用户确认后保存为新版本；
5. 保留原始导入快照。

旧数据不能静默丢失；无法自动迁移的字段必须进入“待确认”清单。

### 8.4 现有资产的保留、改造与替换

重构不是从零重写。当前代码中的数据完整性、存储和导出能力具有复用价值，但需要放到新边界中。

| 当前资产 | 策略 | 说明 |
| --- | --- | --- |
| `integrity.js`、导出 ZIP 与分析窗口逻辑 | 保留并适配 | 先补统一事件 envelope，再迁移派生表计算 |
| Tauri、本地目录、资源存储 | 保留接口，重构适配层 | 上层只依赖 Storage Port，不直接判断 Web/Tauri |
| 会话恢复与单调计时 | 保留行为，重写接口 | 运行状态快照必须引用冻结协议和组件版本 |
| 现有 Flow Engine | 作为迁移参考 | 新执行器直接消费统一图模型，不继续兼容双模型写入 |
| FlowCanvas | 渐进替换 | 可复用交互经验和样式，状态管理改为新图命令系统 |
| Inspector | 替换为 schema 驱动 | 配置项由组件定义生成，特殊组件允许插入专用编辑器 |
| RuntimeContent | 拆分 | 每种组件注册独立运行实现，移除中心化类型分支 |
| QuestionnaireDesigner | 拆为 UI 组件组合与问卷模板 | 问卷成为可复用组合，而不是特殊运行时孤岛 |
| `custom_html` | 仅兼容，不作为首期核心能力 | 旧内容在 sandbox 中运行；新扩展走组件 SDK |
| `domain.js` 旧协议工厂 | 冻结并迁移 | 保留读取与迁移测试，不继续增加新字段 |

### 8.5 关键架构决策

重构开始前应将以下决定写成 ADR（Architecture Decision Record），避免开发过程中反复摇摆：

1. Protocol Graph 是唯一可执行模型，UI 不维护平行 Steps 列表。
2. 控制流和数据流使用不同端口与连接规则。
3. 组件定义采用版本化 schema；组件实例只保存配置与引用。
4. 运行时采用确定性状态机，时间、随机数和外部 I/O 通过可注入端口提供。
5. 原始事件采用 append-only JSONL；CSV 和分析窗口都是可重新生成的派生结果。
6. 参与者 UI 采用声明式组件树；任意脚本不是默认扩展机制。
7. 编辑器修改通过命令产生，命令承担撤销、重做、审计与协作扩展基础。
8. 预览和正式运行共享组件实现，只在时钟、存储和事件出口上使用不同适配器。

### 8.6 建议仓库结构

在当前单仓库中先按模块边界组织，不急于发布多个 npm 包：

```text
src/
├── core/                # schema、图命令、变量、验证、迁移
├── components/          # 内置组件定义及编辑/预览/运行实现
├── editor/              # Composer、Inspector、UI Builder
├── runtime/             # 状态机、时钟、随机数、恢复和事件记录
├── data/                # event schema、派生表、导出、完整性
├── storage/             # Web/Tauri adapters
├── legacy/              # 旧协议读取器与迁移器
└── app/                 # 页面、路由、项目与会话工作流
```

模块之间只通过公开接口依赖。`core`、`runtime` 和 `data` 不得导入 React。

## 9. 分阶段开发计划

### 阶段 0：冻结现状与设计基线（1 周）

产出：用户流程图、术语表、旧模型字段清单、核心用例、迁移策略、性能基线和回归测试基线。

验收：团队能用同一套术语说明“组件、节点、变量、事件、会话、协议版本”。

### 阶段 1：建立核心模型（2 周）

产出：Protocol Graph schema、Component schema、Variable schema、Event envelope、schema validator、migration skeleton。

验收：不依赖 React 即可创建、验证、序列化、反序列化和迁移一个最小实验图。

### 阶段 2：重建运行时内核（2 周）

产出：组件生命周期、控制流执行器、变量作用域、条件和循环、暂停恢复、统一事件记录器。

验收：同一份协议在测试环境中可确定性执行，并能重放同样的分支和事件序列。

### 阶段 3：重建 Composer 编辑器（3 周）

产出：组件库、画布、连接校验、节点选择、基础 Inspector、撤销重做、预览和错误定位。

验收：用户可在 5 分钟内完成“说明—刺激—量表—结束”实验，并能在不阅读 JSON 的情况下修复验证错误。

### 阶段 4：界面构建器（3 周）

产出：Screen、Layout、Text、Media、Input、Button、Progress 等基础 UI 组件，属性绑定和事件动作。

验收：不写 HTML/CSS/JS 即可制作至少三种不同参与者页面，并在运行时正确提交响应。

### 阶段 5：数据契约与导出（2 周）

产出：事件 schema registry、原始事件 JSONL、规范化 CSV、数据字典、配置快照、资源清单、质量报告。

验收：每个内置组件都能展示事件预览；导出包可由独立脚本读取并完成基本数据质量检查。

### 阶段 6：旧协议迁移与试点（2 周）

产出：demo 分支协议迁移器、迁移报告、示例实验、操作员指南、数据分析示例。

验收：现有代表性实验至少 90% 配置可自动迁移；剩余部分有明确人工修复路径。

### 阶段 7：高级扩展（持续迭代）

自定义组件 SDK、组件模板、外部设备、子流程参数化、运行回放、协作和云端能力均在核心稳定后开发。

### 9.1 总体排期与依赖关系

基准计划为 15 周，按 1 名主开发者估算；多人并行时也不能跳过依赖门禁。

| 周期 | 工作包 | 前置依赖 | 阶段出口 |
| --- | --- | --- | --- |
| 第 1 周 | 现状冻结、用例与 ADR | 无 | 模型术语、样例实验和兼容边界获确认 |
| 第 2–3 周 | Core Model | 阶段 0 | schema、图命令和迁移骨架通过测试 |
| 第 4–5 周 | Runtime Kernel | Core Model | 无 UI 执行样例协议并产生确定事件序列 |
| 第 6–8 周 | Composer Editor | Core Model、图命令 | 可创建、编辑、验证并保存 MVP 协议 |
| 第 9–11 周 | UI Builder | Registry、Runtime | 可组合三类参与者页面并真实运行 |
| 第 12–13 周 | Data Contract & Export | Runtime Event | 原始和派生数据可验证、可重建 |
| 第 14–15 周 | Migration & Pilot | 前述全部 | 代表性旧协议迁移并完成试点 |

核心依赖关系：

```text
Protocol Schema ──→ Graph Commands ──→ Composer
       │                    │
       ├──→ Runtime Kernel ─┼──→ Preview / Formal Run
       │                    │
       └──→ Migration       └──→ Undo / Redo / Audit

Component Registry ──→ Inspector / UI Builder / Runtime / Validation / Export
Runtime Events ──→ Raw Log ──→ Integrity ──→ CSV / Analysis Windows / ZIP
```

### 9.2 工作包拆分

每个阶段应拆为可以独立验收的工作包：

- **WP-01 Schema**：协议、节点、边、端口、变量、组件实例和版本 schema；
- **WP-02 Graph Commands**：新增、删除、连接、分组、复制、撤销和序列化；
- **WP-03 Registry**：组件注册、默认值、编辑 schema、运行实现和事件定义；
- **WP-04 Runtime**：执行状态机、时钟、随机化、恢复和失败策略；
- **WP-05 Composer**：组件库、画布、Inspector、验证定位和预览入口；
- **WP-06 UI Builder**：组件树、布局、数据绑定和动作；
- **WP-07 Data**：原始事件、响应投影、分析窗口、数据字典和完整性；
- **WP-08 Legacy**：旧协议读取、映射、迁移报告和只读兼容；
- **WP-09 Pilot**：示例实验、操作员演练、数据核对和发布文档。

每个工作包必须同时提交实现、schema/类型、测试、示例和迁移说明，不能只交付界面。

## 10. 质量与验收指标

### 可用性

- 新用户不看文档，10 分钟内完成最小实验；
- 常用配置路径不超过 3 层；
- 每个错误都能定位到节点、属性或连线；
- 预览结果与正式运行时共享同一组件实现。

### 可扩展性

- 新增一个内置组件只需注册组件定义和实现，不修改核心执行器；
- 组件可声明自己的配置、事件和数据字段；
- 支持 schema 版本和向前迁移。

### 数据可靠性

- 所有运行事件都有 session、protocol version、node/component instance 和 monotonic time；
- 导出包包含原始事件、规范化表格和数据字典；
- 随机化、变量计算、异常、暂停、恢复、跳过和重试均可追溯；
- 断电或刷新后不会静默丢失已确认响应。

### 性能

- 500 节点级别画布可正常编辑；
- 10,000 个事件的会话可以导出；
- 页面切换、节点拖拽和输入编辑不因全量协议重渲染而明显卡顿。

## 11. 风险与控制

### 风险：重构范围过大

控制：先建立兼容层和最小图模型；旧编辑器可以暂时只读，禁止同时维护两套可写模型。

### 风险：无限制自定义导致安全和稳定性问题

控制：首期使用声明式 UI 组件和事件动作；脚本扩展必须进入受限 sandbox，并具备权限和事件 schema。

### 风险：自由布局增加跨设备差异

控制：先提供有限布局容器、约束、断点和安全区域；不要首期开放任意绝对定位。

### 风险：完整日志造成数据量膨胀

控制：区分基础、详细和高频三种采集级别；原始日志与分析派生表分离。

### 风险：迁移破坏既有实验

控制：保留原始协议快照、自动生成迁移报告、迁移前后结构 diff，并要求正式运行只能使用冻结版本。

### 风险：研究数据隐私

控制：参与者标识、外部 URL、媒体和设备数据分级管理；导出前显示敏感字段清单；默认不把不必要的个人信息写入日志。

## 12. 首个可交付版本定义

首个重构版本不追求覆盖当前全部 Step 类型，而追求完成一条可信的端到端路径：

```text
拖入组件 → 连接流程 → 配置参与者页面 → 预览
→ 验证 → 冻结 → 运行 → 产生统一事件 → 导出可分析数据包
```

建议首批只实现：说明、媒体、固定等待、量表、按钮、文本输入、条件、循环、结束、变量、基础布局和事件导出。问卷、外部表单、生理设备和复杂自定义脚本在这个闭环稳定后逐步接入。

## 13. 立即执行的任务清单

1. 建立 `core-model` 的 schema 和 migration 测试，不再新增 Step 类型分支。
2. 绘制旧模型到新模型的字段映射表。
3. 定义首批 8–10 个组件的统一接口和事件 schema。
4. 将现有运行时事件归一化为统一 envelope。
5. 实现最小图模型到运行时的纯函数执行器。
6. 为“说明—刺激—量表—结束”建立 Composer MVP 原型。
7. 为该原型补齐从创建到导出的端到端测试。
8. 在迁移器完成前冻结旧协议写入格式，避免继续扩大兼容成本。

## 14. 成功标准

重构成功的标志不是代码文件变少，也不是节点类型更多，而是：

- 普通用户可以快速搭建实验；
- 高级用户可以扩展组件而不修改核心系统；
- 参与者界面可以由用户组合，而不是只能选择预制页面；
- 实验逻辑、界面行为和数据记录彼此可追踪；
- 同一协议可以稳定预览、运行、恢复、重放和导出；
- 每一条分析数据都能追溯到协议版本、组件实例和运行事件。

## 15. 测试与验证计划

### 15.1 测试层级

- **Schema 测试**：合法/非法协议、版本迁移、未知字段和向前兼容；
- **图命令测试**：节点和连线操作、撤销重做、ID 稳定性和引用完整性；
- **运行时测试**：顺序、条件、循环、随机化、暂停、恢复、跳过、重试和异常；
- **组件契约测试**：输入、输出、完成条件、事件和导出字段；
- **数据测试**：原始事件到 CSV/窗口/完整性报告的确定性投影；
- **编辑器集成测试**：拖入、连接、属性编辑、预览、保存和重新打开；
- **端到端测试**：设计、冻结、正式运行、恢复和导出完整闭环；
- **可用性测试**：至少邀请初学者和有实验经验的用户分别完成代表任务。

### 15.2 基准实验集

持续集成至少覆盖以下协议：

1. 说明—图片—评分的最小实验；
2. 随机刺激与反应时任务；
3. 带条件跳转和注意力检查的问卷；
4. 有循环、暂停恢复和操作员标记的实验；
5. 从旧版本迁移的生理实验协议；
6. 资源缺失、事件中断和无效配置等失败样例。

每个基准实验保存预期事件序列和导出快照，用于发现语义回归，而不仅是 UI 截图变化。

### 15.3 Definition of Done

一个功能只有满足以下条件才算完成：

- 需求和非目标明确；
- schema、迁移和错误处理已定义；
- 单元测试和关键集成测试通过；
- 预览与正式运行行为一致；
- 新事件和导出字段进入数据字典；
- 无障碍键盘路径和多语言回退可用；
- 文档和至少一个可运行示例已更新；
- 不引入对旧双模型的新写入依赖。

## 16. 发布、迁移与回滚

### 16.1 发布策略

- 新架构首先作为实验性工作空间启用，不覆盖现有正式采集入口；
- 协议保存时写入明确的 `schema_version` 和应用版本；
- 每个候选版本先完成基准实验自动测试，再做一次真实操作员演练；
- 正式版本仅运行冻结协议，冻结后资源和组件版本不可隐式变化。

### 16.2 迁移策略

- 迁移采用“复制并转换”，绝不原地覆盖旧协议；
- 输出字段映射、丢失字段、默认值和人工确认项；
- 新旧运行结果通过事件序列与导出表进行对照；
- 未通过迁移验证的协议继续使用旧运行时只读执行。

### 16.3 回滚策略

- 应用升级不得自动重写全部项目；
- 保留旧 schema reader 和上一个稳定运行时；
- 发布失败时回滚应用版本，但不删除新格式数据；
- 会话事件采用 append-only，恢复操作追加事件而不修改历史事件。

## 17. 项目治理与决策机制

### 17.1 文档基线

以下文档应与代码共同版本管理：

- 产品术语表和核心用户旅程；
- Protocol、Component、Variable、Event schema；
- ADR；
- 旧到新字段映射；
- 组件目录及数据契约；
- 发布检查表和迁移说明。

### 17.2 变更规则

- 新组件进入核心库前必须说明通用性，实验专用组合优先做模板；
- 修改事件字段必须升级 schema 并提供迁移或兼容说明；
- 任何会改变正式实验行为的修改必须增加回归样例；
- UI 功能不能绕过核心图命令直接修改协议对象；
- 发现模型问题时优先修复抽象，不通过添加新的特殊布尔字段规避。

### 17.3 评审节奏

- 每周一次产品与模型评审：确认用户路径和领域概念；
- 每个阶段结束进行门禁评审：只有达到出口标准才进入下一阶段；
- 每两周用真实实验协议演示，不以孤立组件演示代替端到端验证；
- 试点阶段由设计者、操作员和数据分析人员分别签收对应业务结果。

## 18. 关键指标

重构后的产品效果使用以下指标评估：

| 维度 | 指标 | MVP 目标 |
| --- | --- | --- |
| 上手效率 | 从新项目到可预览最小实验的中位时间 | ≤ 10 分钟 |
| 编辑效率 | 常用节点完成配置所需的主要操作数 | ≤ 8 次 |
| 清晰度 | 用户无需帮助完成核心任务的比例 | ≥ 80% |
| 正确性 | 基准实验运行事件与预期一致率 | 100% |
| 数据完整性 | 正式会话通过关键完整性检查比例 | ≥ 99% |
| 可迁移性 | 代表性旧协议自动迁移字段覆盖率 | ≥ 90% |
| 可扩展性 | 新增标准组件需要修改的核心模块数 | 0 |
| 可恢复性 | 注入中断后成功恢复并保留已确认数据 | 100% |
